MASTER PROMPT — AFUCHAT COMPLETE MULTI-LANGUAGE / LOCALIZATION FIX

You are working on AfuChat, a multilingual social platform. The platform supports users from different countries and users can use AfuChat in different languages.

CURRENT PROBLEM:
The language system is partially working. Some text is translated when the user changes language, but many other UI texts remain in English.

For example, on the profile/account screen, some text is translated into the selected language while labels such as:

- SUBSCRIPTION
- MY CONTENT
- SOCIAL & GROWTH
- My
- Saved
- Watch
- Digital ID
- Premium
- platinum
- buttons
- navigation labels
- section headings

remain in English.

THIS IS NOT ACCEPTABLE.

Do NOT solve this by translating only the visible screen. We need to fix the localization architecture across the ENTIRE AFUCHAT PLATFORM.

==================================================
1. FIRST: AUDIT THE EXISTING LOCALIZATION SYSTEM
==================================================

Before changing code, inspect the existing localization/i18n implementation.

Determine:

- Which i18n/localization library is currently being used.
- Where supported languages are defined.
- Where translation files are stored.
- How the current language is saved.
- How the current language is loaded on app startup.
- How translations are accessed from components.
- Whether translations work consistently between screens.
- Whether translations are coming from the frontend, backend, database, or hardcoded strings.
- Whether there are duplicate translation systems.
- Whether there are components bypassing the translation system.
- Whether some screens use translation keys while others use hardcoded English.

Do not replace the existing localization library unnecessarily.

If the current localization architecture is usable, improve it instead of creating a completely separate system.

AfuChat is a multilingual platform.

==================================================
5. EVERY SUPPORTED LANGUAGE MUST HAVE COMPLETE COVERAGE
==================================================

A translation key existing in English must not silently remain English in another supported language unless it is intentionally marked as untranslated.

Create a mechanism to detect missing translations.

Example:

English:

profile.saved = "Saved"

Amharic:

profile.saved = "..."

Swahili:

profile.saved = "..."

If a translation is missing, the development system should be able to identify it.

Create a translation audit/report that can show:

- Missing keys
- Extra keys
- Duplicate keys
- Empty translations
- Invalid translation files

Do NOT allow missing translations to go unnoticed.

==================================================
6. ENGLISH SHOULD BE THE FALLBACK LANGUAGE
==================================================

Implement a safe fallback.

If:

selected language = Amharic
AND
Amharic translation is missing

then temporarily fall back to English.

However, this fallback should be detectable during development.

Do not silently accept missing translations as a finished implementation.

The goal is:

100% coverage of user-facing UI strings.

==================================================
7. DO NOT TRANSLATE DATA THAT SHOULD NOT BE TRANSLATED
==================================================

Do NOT translate user-generated or identity-specific content automatically unless AfuChat specifically has a translation feature for it.

Examples that normally should NOT be translated:

- Usernames
- Display names
- Brand names
- AfuChat
- AfuAI
- AfuMall
- Product names
- Company names
- URLs
- Email addresses
- User-generated post content
- User-generated comments
- Chat messages
- Group names

The localization system is primarily for AfuChat's own interface.

If user-generated content translation exists, keep that as a separate explicit feature.

==================================================
8. DO NOT HARD-CODE TRANSLATED TEXT INSIDE COMPONENTS
==================================================

Bad:

<Text>የእኔ ይዘት</Text>

Bad:

<Text>My Content</Text>

Good:

<Text>{t("profile.my_content")}</Text>

The component should not care what language is being displayed.

The translation layer decides the actual text.

==================================================
9. HANDLE DYNAMIC TEXT CORRECTLY
==================================================

Do not build sentences by concatenating translated strings.

Bad:

<Text>{t("hello")} + " " + username</Text>

Use interpolation:

<Text>
  {t("welcome_user", { name: username })}
</Text>

Translation:

{
  "welcome_user": "Welcome, {{name}}"
}

The same key can then be translated correctly in other languages where sentence structure differs.

==================================================
10. HANDLE PLURALS CORRECTLY
==================================================

Do not hardcode English plural logic.

Bad:

`${count} message${count > 1 ? "s" : ""}`

Use the localization system's pluralization support.

Examples:

messages_one
messages_other

or the equivalent supported by the existing i18n library.

Languages have different plural rules, so the system must allow each language to define its own correct plural form.

==================================================
11. DATES, TIMES AND NUMBERS
==================================================

Localized formatting must be used for:

- Dates
- Times
- Relative dates
- Numbers
- Percentages
- Currency
- Durations

Do not assume English formatting everywhere.

Use locale-aware formatting.

Examples:

1,000
1.000
1 000

may vary by locale.

Dates and times must also respect the user's locale where appropriate.

==================================================
12. RTL LANGUAGE SUPPORT
==================================================

The architecture must support right-to-left languages.

Do not assume every language is left-to-right.

If AfuChat supports or plans to support Arabic, Hebrew, Persian, Urdu, etc., the UI must be capable of switching direction.

The developer must review:

- Layout direction
- Text alignment
- Icons
- Back buttons
- Navigation
- Padding
- Margins
- Flex direction
- Lists
- Chat bubbles
- Forms
- Headers
- Bottom navigation

Do not simply reverse the entire UI blindly.

Use proper RTL support provided by the framework.

13. LANGUAGE SWITCHING
==================================================

When the user changes language:

1. Save the selected language.
2. Update the localization instance.
3. Update the UI immediately.
4. Ensure all mounted components rerender.
5. Ensure navigation labels update.
6. Ensure menus update.
7. Ensure modals update.
8. Ensure buttons update.
9. Ensure placeholders update.

==================================================
14. LANGUAGE PERSISTENCE
==================================================

The selected language must persist.

For example:

User selects Amharic
→ closes app
→ opens AfuChat again
→ AfuChat should still use Amharic.

Use the appropriate persistent storage mechanism already used by the application.

Also ensure there is a sensible first-launch language selection strategy.

If AfuChat uses device/browser language detection, it can use that as the initial default, but the user's explicit choice must take priority afterward.

Priority should generally be:

1. User's saved AfuChat language preference
2. Device/browser language
3. AfuChat default language

==================================================
15. BACKEND-GENERATED TEXT
==================================================

Audit the backend/API responses too.

If the backend sends user-facing English strings such as:

"Payment successful"
"User not found"
"Something went wrong"
"Subscription expired"

do not blindly assume the frontend can translate arbitrary sentences.

Prefer structured error/message codes.

Example:

{
  "code": "SUBSCRIPTION_EXPIRED"
}

Then the frontend translates:

t("errors.subscription_expired")

This allows the same backend response to work correctly in every supported language.
