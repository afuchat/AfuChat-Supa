# AfuChat — Critical Online Performance, Realtime & Notification Fix

You are a senior React Native, Expo, Supabase Realtime, Android performance, and push-notification engineer.

AfuChat has a critical production problem that must be diagnosed and fixed at the architectural level.

## The Most Important Observation

The behavior is now clearly established:

### When AfuChat is offline:

* The application is fast.
* Navigation is responsive.
* Back buttons respond normally.
* Pages open normally.
* Chats open normally.
* Buttons respond normally.
* The application feels smooth.

### When AfuChat is online:

* The application initially opens fast.
* Once network data starts arriving, performance begins to deteriorate.
* The more realtime/data activity occurs, the slower the application becomes.
* Eventually even basic interactions become extremely slow.
* Opening chats becomes slow.
* Opening pages becomes slow.
* Navigation becomes slow.
* Back buttons become slow.
* Saving becomes slow.
* Tapping UI elements can feel delayed or completely unresponsive.

### Critical conclusion

**Do NOT treat this as a general navigation-performance problem.**

The strongest hypothesis is that incoming network/realtime data is causing excessive:

* JavaScript execution
* state updates
* React rerenders
* realtime event processing
* database requests
* cache updates
* subscriptions
* listeners
* memory usage
* data transformations

The app is fast when the incoming workload disappears.

Therefore, the first priority is to identify exactly what happens when AfuChat goes from:

```text
OFFLINE
↓
FAST
```

to:

```text
ONLINE
↓
DATA ARRIVES
↓
PROCESSING INCREASES
↓
RENDERS/STATE UPDATES INCREASE
↓
JS THREAD BECOMES BUSY
↓
ENTIRE APP BECOMES SLOW
```

# 8. INVESTIGATE PRESENCE

The notification system currently has another serious problem:

A user can be actively using AfuChat, but the system can treat the user as offline.

Do not use one simplistic:

```text
user.online = true
```

value as the entire presence system.

Presence must account for:

* active app session
* background state
* disconnected state
* reconnection
* multiple devices
* network interruption

Do not update the database on every user interaction.

Throttle activity updates.

---

# 9. DO NOT USE PRESENCE AS THE ONLY PUSH-NOTIFICATION DECISION

Do NOT implement:

```text
if online:
    don't send notification
else:
    send notification
```

based solely on Realtime Presence.

A Realtime connection is not the same thing as:

> "The user is currently looking at this conversation."

The notification system must distinguish between:

```text
User active + viewing this conversation
User active + viewing another screen
User backgrounded
User offline
```

Example:

```text
User is active
+
Viewing John's conversation
+
John sends message
=
Update chat UI
No unnecessary push
```

But:

```text
User is active
+
Browsing Discover
+
John sends message
=
Push/notification should be allowed
```

# 22. FINAL RULE

Do not declare the application optimized because:

> "It opens quickly."

That is not the problem.

The real requirement is:

> **AfuChat must remain fast after it connects, starts receiving real user data, and continues running realtime systems.**

The current behavior proves that the application is fast when the data workload is absent.

Therefore:

**Find what incoming data is doing to the application.**

Measure it.

Identify the exact bottleneck.

Fix the architecture.

Then verify it on a real low-performance Android device using a production release build.

The final result must be:

**Fast offline → Fast online → Fast under realtime activity → Fast on low-end Android → Stable for long sessions → Reliable notifications.**
