Fix AfuChat Android push notifications for ALL supported Android devices, not just the current test device.

Package:
com.afuchat.afuapp

The current physical test device is Android 15, but the implementation must be production-safe across Android versions and manufacturers, including Samsung, Tecno/Infinix, Xiaomi/Redmi, Oppo/Realme, Vivo, Huawei where Google Play Services are available, and other standard Android devices.

CURRENT DIAGNOSIS

ADB confirms:

1. POST_NOTIFICATIONS is granted:

2. Firebase initializes successfully:
FirebaseApp: Device unlocked: initializing all Firebase APIs for app [DEFAULT]
FirebaseInitProvider: FirebaseApp initialization successful

3. Firebase Messaging exists in the APK:
com.google.firebase.iid.FirebaseInstanceIdReceiver
expo.modules.notifications.service.ExpoFirebaseMessagingService
com.google.firebase.messaging.FirebaseMessagingService

4. However, logcat shows no evidence of:
- FCM token generation
- FirebaseMessaging.getToken()
- registration token
- token refresh
- FCM message reception

Therefore, investigate and fix the COMPLETE notification architecture instead of assuming this is a permission problem.

GOAL

AfuChat must reliably receive and display push notifications on all supported Android devices.

The complete flow must work:

AfuChat event
→ backend notification trigger
→ FCM HTTP v1
→ correct Firebase project
→ correct device FCM registration token
→ Firebase Messaging
→ Android notification channel
→ notification shade

IMPLEMENTATION REQUIREMENTS

1. FCM TOKEN

Implement one reliable native FCM token registration flow.

The app must:

- initialize Firebase Messaging
- request notification permission when required
- obtain the native FCM registration token
- persist the token
- associate it with the authenticated AfuChat user
- upload/update it in Supabase
- handle token refresh automatically
- support multiple devices per user
- invalidate/remove tokens on logout where appropriate

Do NOT confuse:
- Expo Push Token
- Expo device token
- FCM registration token

The backend must receive and store the actual FCM registration token if we are using direct FCM.

2. TOKEN LIFECYCLE

Handle:

- first installation
- first app launch
- login
- logout
- reinstall
- app update
- Firebase token rotation
- device restore
- account switching
- multiple accounts/devices
- expired/invalid FCM tokens

Do not assume an FCM token remains permanent.

3. FIREBASE CONFIGURATION

Verify the release/production Android build contains the correct Firebase configuration.

Check:

- package name: com.afuchat.afuapp
- Firebase Android app registration
- project ID
- application ID
- sender ID
- google_app_id
- gcm_defaultSenderId
- google-services.json
- Gradle Google Services plugin
- EAS/build configuration
- release signing/build configuration

Make sure the Firebase project used to generate the device token is the SAME Firebase project used by the backend to send notifications.

4. BACKEND

Audit the notification backend.

Confirm that:

- FCM HTTP v1 is used correctly
- the correct Firebase service account is used
- the service account belongs to the same Firebase project
- the stored token is an FCM registration token
- notifications target the correct token
- invalid/unregistered tokens are removed
- backend errors are logged
- token delivery failures are distinguishable from application errors

Handle FCM responses such as:

UNREGISTERED
INVALID_ARGUMENT
SENDER_ID_MISMATCH
THIRD_PARTY_AUTH_ERROR
QUOTA_EXCEEDED
UNAVAILABLE

Do not silently ignore FCM failures.

5. ANDROID NOTIFICATION CHANNELS

Implement proper Android notification channels.

Create required channels on app startup.

Use stable channel IDs.

Set appropriate:
- importance
- sound
- vibration
- badge behavior

Make sure every notification sent by AfuChat references a valid channel.

Do not create hundreds of channels dynamically.

6. ANDROID VERSIONS

Support notification behavior across Android versions.

Android 13+:
- request POST_NOTIFICATIONS

Android 8+:
- notification channels

Older supported Android versions:
- use the appropriate legacy behavior

Do not assume Android 13+ behavior applies to older versions.

7. MANUFACTURER-SPECIFIC BEHAVIOR

The implementation must be robust against manufacturer battery/background restrictions.

Pay special attention to:

Tecno/Infinix/Transsion
Samsung
Xiaomi/Redmi/POCO
Oppo
Realme
Vivo
OnePlus

Do not implement unsafe hacks or instruct users to disable battery optimization globally.

Notifications must work normally whenever the OS permits background delivery.

If a manufacturer has known restrictions, handle them gracefully rather than breaking the normal Android implementation.

8. FOREGROUND / BACKGROUND / TERMINATED

Test and support:

A. App open in foreground
B. App in background
C. App completely terminated
D. Device locked
E. Device restarted

For foreground messages, explicitly implement notification presentation if required.

For background/terminated messages, ensure the native Firebase Messaging service receives the message and Android displays the notification.

9. PAYLOAD DESIGN

Audit the FCM payload.

Use a consistent payload structure.

For example:

notification:
  title
  body

data:
  type
  conversationId
  senderId
  notificationId
  deepLink

Make sure data values are strings where required by FCM.

Do not rely on JavaScript being alive to display a notification when the app is backgrounded/terminated.

10. EXPO MIGRATION

AfuChat previously used Expo Push Notifications but has moved toward direct FCM.

Audit the current Expo notification configuration.

The APK currently contains:

expo.modules.notifications.service.ExpoFirebaseMessagingService

and:

com.google.firebase.messaging.FirebaseMessagingService

Determine whether both are necessary.

If AfuChat is now using direct FCM, remove obsolete Expo Push notification logic/configuration where safe.

Do not maintain two competing token systems.

There must be ONE clearly defined production notification architecture.

11. STORAGE

There is currently this error:

[MMKV] Failed to initialise persistent store — falling back to in-memory. All data will be lost on restart.

Investigate whether notification tokens/settings depend on MMKV.

Fix persistent token storage if necessary.

However, the database should remain the source of truth for server-side device tokens.

Do not permanently expose full FCM tokens in production logs.

13. SUPABASE

Audit the device token database structure.

It should support multiple devices per user.

Do not store only one token per user if the user can have multiple Android devices.

A suitable model should conceptually support:

user_id
device_id
platform
fcm_token
app_version
os_version
last_seen
created_at
updated_at
active

Use unique constraints appropriately so token updates do not create duplicates.

14. SECURITY

Never put Firebase service account private keys inside the Android application.

FCM sending credentials must remain server-side.

The Android app should only contain public Firebase client configuration.

15. RETRY / FAILURE HANDLING

Implement reasonable retry behavior for temporary FCM/network failures.

Do not create infinite retry loops.

If a token is invalid/unregistered, mark it inactive/remove it rather than repeatedly sending to it.

16. DO NOT BREAK EXISTING FEATURES

Do not regress:

- chat
- realtime
- offline synchronization
- navigation
- authentication
- Supabase
- existing notification actions
- deep links
- app performance

The app has recently become significantly faster, so avoid introducing heavy polling or permanent background processes.
